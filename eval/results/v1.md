## 해석 (작성: 실행 후, acceptance 기준은 실행 전 커밋 `ee3faa0`에 고정)

- **이 작업군으로는 성공률 차이를 판별할 수 없다.** claude 20/20, codex 19/20으로 천장에 붙었다. 쌍당 1회 실행이라 통계적 주장은 하지 않는다. 판별하려면 더 어려운 작업(다중 파일 수정, 실패하는 기존 테스트, 긴 컨텍스트)과 반복 실행이 필요하다.
- **bench-router는 20개 중 18개에서 fixed-default와 같은 선택을 했다.** 12개는 근거 부족(`default_insufficient_evidence`)이었다. coding_repo·terminal_ops·code_gen·webdev는 AA `coding_index`가 null이고 SWE/TB exact 데이터가 없어 coverage가 0이다. 지금 라우터의 한계는 정책보다 **evidence coverage**에 있다.
- 정책이 갈린 2개(general: checklist, translate)에서는 bench-router가 codex를 골랐고 둘 다 성공했다. 대가는 평균 시간 +2.3초(38.6 → 40.9), 이득은 cost proxy −1.0(20 → 19)이다. cost proxy는 정책상 tier 값이고 **실제 요금이 아니다.** 실제 비용(구독·토큰)은 측정하지 않았다.
- 지연: codex 실행이 전 작업에서 더 길었다(평균 83.9초 대 38.6초, Agent 시작 포함 wall time). rotate는 233초.
- 유일한 실패(logs / codex)는 형식 해석 차이다. `top_errors`를 문자열 리스트가 아닌 `{message, count}` 객체 리스트로 썼다. 프롬프트의 "상위 3개 리스트"에 원소 형식을 명시하지 않은 **과제 명세의 모호함**도 원인이다. 사전에 고정한 기준대로 실패로 집계했다.
- 같은 실패에서 Agent는 `status: success`라고 자기보고했다. Subagent 자기보고를 성공으로 바꾸지 않는다는 설계(04 문서)가 실제로 필요하다는 근거다.
- 라우터 자체: 40/40 `completed`, blocked 0, 결과 계약 위반 0, 열린 workspace 0.
