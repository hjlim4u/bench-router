# Bench-router handoff

Use this skill only for a task the caller wants to hand off. The router evaluates and validates the selected profile, then dispatches through Herdr, a local subprocess or the caller (external runner), owns receipts and collects results. The caller still verifies the work and records feedback.

## Setup

- This skill contains instructions and references only. Install them globally with `npx skills add hjlim4u/bench-router -g` or project-locally without `-g`; both scopes may coexist.
- Use the shared `bench-router` command from any working directory. Install the runtime once per user with `uv tool install /absolute/path/to/bench-router` (or `uv tool install git+https://github.com/hjlim4u/bench-router.git`). `bench-router-decide` is installed alongside it. Do not copy the engine into a skill or project, or install it into each project's virtualenv. If the command is missing, check PATH (`uv tool update-shell`) and the shared installation.
- Run `bench-router init` once to create shared default profiles and aliases offline; existing files are preserved. Benchmark data is fetched separately with `bench-router refresh --source mg` when requested.
- Use the same runtime user's default config (`~/.config/bench-router`) and cache (`~/.cache/bench-router`) across agents, unless the operator has deliberately set shared `XDG_CONFIG_HOME` and `XDG_CACHE_HOME`. Keep all agents sharing a cache on one OS runtime; native Windows and WSL use different lock implementations and must not concurrently point at the same physical cache. Do not create agent-specific caches or copy snapshots.
- Selection needs only `profiles.toml` (schema 2.0 can list caller-owned API or host-tool agents without CLI fields). Live dispatch runs on Linux/WSL2. The Herdr runner needs Herdr, herdr-projects 1.2.1 and the agent CLI; the `local` runner needs only the agent CLI, and `external` needs neither (see Runners). The task `cwd` must be the top level of a git repository with a commit. Profile `args` may only carry a model (`--model`/`-m`) and an effort; agent permissions follow the board's `worker.access` setting. Run `bench-router status` to inspect snapshot health. Use `bench-router COMMAND --help` for command contracts.

## Delegate and recover

Use the [vendor-guided decision workflow](references/decision.md) for semantic facets, suitability and benchmark relevance: Jev when `TYPESAFE_API_KEY` (or `JEV_API_KEY`) is set, otherwise the host's native `bench-decider` (Antigravity Flash, Codex GPT-6 Luna, Claude Code Haiku). The caller makes the final choice among suitable profiles. Pass the current host through `bench-router-decide --host antigravity|codex|claude`; `BENCH_ROUTER_DECISION_MODEL` overrides its model. Read that reference before choosing; the helper implements provider detection and response validation. Do not send these decisions through Router delegation or recursively invoke this Skill.

1. Create a temporary UTF-8 JSON task file with `schema_version: "1.0"`, a unique `task_id` (UUID hex is suitable), `round: 1`, `summary`, `prompt`, and an existing, trusted absolute `cwd`. Add only relevant optional task fields. Keep the task content and `(task_id, round)` stable for retries; use a new round only after checking the previous run's effects. Remove the temporary file once its CLI output is captured.
   When the user names a model, an effort or a vendor to use or avoid, put it in `profile_filter` instead of starting a full selection: `{"include": {"model": ["gemini-3.8-flash"], "effort": ["high"]}}` (exact IDs from `profiles.toml`; also `vendor`, and `exclude` with the same axes). One included model and one included effort that leave a single eligible profile skip every decision stage and record `user_specified`; a named model alone asks only its vendor's guide for the effort and skips the benchmark review once one suitable effort remains. No matching profile returns `no_eligible_profile`; never drop the filter to retry.
   Supply explicit `facets` (`{axis: [value]}`) only from `bench-router wiki facets`. The router batches unresolved semantic facets and workload analysis in its first stage; do not run a duplicate facet pass. It judges exact model/effort suitability without benchmark scores, retrieves relevant evaluations, checks measurement conditions, and reviews relevance without candidate scores. It returns per-unit comparisons without combining votes. Unknown facets fail with the allowed list.
   Before interpreting missing metrics, check `status`. When sources need checking, add `--refresh` to the initial `evaluate` below and inspect `benchmark_refresh.sources`; remove it for every response replay. A failed fetch retains last-good until max_stale. Same-vendor nearby measured proxies require a recent source check and retain donor model/effort, scope and stale markers. They do not prove the requested profile's quality. Inspect `comparison_profiles` rather than assuming every candidate participated. Task priority remains part of vendor guidance; contextual interactive recommendations apply only to their recorded inputs.
2. Run `bench-router evaluate --format 3 --task TASK_FILE --host HOST` to obtain the current stage packet. Follow the reference, save `{"stages": [<decision.completed entries>, <current response>]}`, and repeat with `--decision-response RESPONSE_FILE` until the assessment is `ok`. Choose among suitable candidates using the task requirements, observations and reported uncertainty. Save the assessment, run `select --assessment ASSESSMENT_FILE --profile PROFILE --policy-id POLICY --policy-version VERSION --reason REASON` (add `--accept-provisional` when needed), save its `selection` object, and execute `route --task TASK_FILE --selection SELECTION_FILE`. A direct `route` may select a sole suitable profile without pending conditions; multiple candidates or evaluation-only efforts return `decision_unavailable` and `upstream_selection_required`. Pass global options such as `--herdr-session` before `route` when needed. Read the JSON `status` even when the process exits nonzero, and retain `run_id` and `cwd` for recovery. Add `--dry-run` to validate selection without dispatch. Plain `route` uses the `vendor-guided` policy. `decision_required` and `decision_unavailable` use exit 17. Never silently switch policies.
3. For `blocked`, address the reported approval or question through the normal caller workflow. For `timed_out` or `delivery_uncertain`, run `collect --run-id RUN_ID --cwd CWD --wait-ms N`; never generate a fresh task ID or resend the prompt to resolve uncertainty. For `conflict`, inspect the warning and existing receipt before another dispatch. A completed result means the artifact contract passed, not that the task succeeded.
4. A `completed` run's agent panes are closed automatically so finished agents stop holding resources (`release` in the output; agents still working or blocked are left open). To continue that agent's conversation, run `bench-router resume --run-id RUN_ID --cwd CWD`; it reopens the board task's space and restarts the agent in the same session without sending anything.
5. Inspect the returned result and verify the requested work. Record the verified outcome with `feedback --run-id RUN_ID --cwd CWD --outcome success|partial|fail` when there is a run to assess.

## Runners (Herdr optional)

The global `--runner auto|herdr|local|external` option (default `auto`, or `BENCH_ROUTER_RUNNER`) picks the executor for live `route`/`parallel`. `auto` uses Herdr when `herdr-projects` is on PATH, otherwise `local`. Every runner keeps the same receipt, admission limit, `collect` and result contract, and a recorded run always recovers through its own runner (`backend` in the output).

- `herdr`: board agent (`interactive`) or Herdr pane (`headless`), as described below.
- `local`: runs the profile's one-shot CLI (`claude -p`, `codex exec`, `agy -p`) as a local subprocess in a router worktree. Only `"execution": "headless"` tasks are accepted. `stop` ends the process; `tell` and `resume` are not available.
- `external`: the router prepares the worktree, prompt and receipt and returns `handed_off` (exit 11) with an `invocation` (`cwd`, `prompt_path`, `result_dir`, suggested `argv`, `model_id`, `deadline_at`). Run the agent yourself (API, subprocess, host Agent tool), have it write the result files into `result_dir`, then `collect`. Use `stop` to record that your agent stopped. Local CLI availability is not probed, and schema 2.0 caller-owned profiles are eligible.

To only select, finish steps 1–2 and run `route --task TASK_FILE --selection SELECTION_FILE --dry-run`.

## Parallel handoff

Default to `route`. Use `parallel` only when independent subtasks or a comparison of approaches is worth the cost: it starts tasks × fanout agents.

For several subtasks or a best-of-N attempt, assess each task and choose profiles upstream using `select`. Write a schema 2.0 group with `group_id`, git top-level `cwd`, and `tasks: [{task: TASK_WITHOUT_CWD, selections: [SELECTION, ...]}]`; selection count sets fanout and profiles may repeat. Run `bench-router parallel --group GROUP_FILE` (`--dry-run` to validate). Each agent works in its own git worktree. The member's `receipt_cwd` is `<cwd>/.bench-router/groups/GROUP/members/LABEL`; use it with control commands. No worktrees or workers are created while any choice is pending or stale. A saved live group plan freezes selections and runner choice for recovery. Choose `isolation`: `isolated` (no sharing) or `shared` (agents share a scratchpad). Review rounds and voting are the orchestrator's job. Rerun the same group file to recover; it never resends prompts. Compare and merge the member branches yourself, then remove their worktrees.

- Worktrees start from `HEAD`; uncommitted changes in `cwd` are not included (`dirty_base` warning).
- The main repository must already be trusted in each agent CLI; otherwise agents report `blocked` at startup. Worktrees under a trusted repository were not asked again.
- A member that was `blocked` before its prompt is not resent by rerunning the same group. Resolve the cause, then use a new `group_id` or `round`.

## Projects collaboration

Use ordinary `route` tasks for implementation, review and revision. Pass earlier artifacts explicitly in each new round. For blocked work use the returned board task ID (`thread_id`, e.g. `repo/12`) with `herdr-projects details`, and answer it on the board through the caller's normal approval workflow. Never delegate, retry or tell the task directly to recover a Router submission. To steer a live run, send one explicit message with `bench-router tell --cwd CWD [--run-id RUN] --message TEXT` (for a parallel member, `--cwd` is its `receipt_cwd` `<cwd>/.bench-router/groups/<group_id>/members/<label>`); it is logged in `runs/RUN/messages.jsonl`, and a settled run needs `resume` first. Pass `--wait-ms 0` to `route`/`parallel` to get run IDs right after submission, then compose patterns (relay, broadcast, best-of-N, review rounds) yourself; the router implements none. Two control utilities help: `bench-router collect --run CWD RUN_ID --run … --until any|all --wait-ms N` waits for the first or all runs, and `bench-router stop --cwd CWD [--run-id RUN]` stops a live run (it then collects as `execution_failed`). For a parallel member, CWD is its `receipt_cwd`. A task with `"execution": "headless"` runs a one-shot CLI (`claude -p`, `codex exec`, `agy -p`) with approvals off in its own herdr worktree pane, shown on the board without an agent; it takes no `tell`. All Router executions share durable task binding, the four-active limit and the overlapping-workspace guard. Verify results and record `coordination feedback` separately; do not delegate recursively. Shared scratchpads sit outside each agent's worktree; with `worker.access ask` every write there needs approval.

## Concurrent vendor decisions

When `decision.requests` is present, launch one native `bench-decider` per packet concurrently using the host's parallel tool mechanism. Send each agent only `packet.request`, verify its requested model, and attach that packet's `request_digest` to its reply. Preserve `decision.completed` and append all newly completed responses under `stages`; guidance reply order is arbitrary. Partial failure requests only missing vendors. Never combine vendor packets into one prompt. Live Jev calls already run concurrently inside the router.

## Shared data

Routing reads the shared snapshot. One user-level scheduled `refresh` can keep data current; initial `evaluate --refresh` explicitly checks due sources before assessing missing metrics. Plain evaluation and response replay remain offline. SWE/TB still need approved manual imports. Concurrent refreshes and dispatches to the same `cwd` return a busy/conflict result; do not work around their locks. See `status` and the JSON warnings for stale or missing evidence.
